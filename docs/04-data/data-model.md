# Data Model

The Telegram data model is a normalized projection of TDLib, not a raw TDLib
archive and not a generic message feed.

This document defines the target model. Implementation can lag behind it, but
new Telegram ingestion work must move toward this model and must not add a
parallel raw-event architecture as the durable source of truth.

## Coverage Baseline

The coverage baseline is the official TDLib schema file:

- TDLib schema source:
  `https://raw.githubusercontent.com/tdlib/td/49b3bcbb6bfebf2ed44dd9f25102d2e1a94a58c4/td/generate/scheme/td_api.tl`
- TDLib schema commit: 49b3bcbb6bfebf2ed44dd9f25102d2e1a94a58c4
- TDLib schema SHA-256:
  1a0d13cebb0c04a866da3aac55bb6b47b084b4a789877ab019348c5374f4f2d2
- Object constructors: 2055
- Object result types: 713
- Updates: 180/180
- Functions: 990/990
- Function return types: 279
- MessageContent constructors: 100/100

Coverage is checked by:

```bash
node scripts/tdlib-data-model-audit.mjs
```

Field-level routing is generated by:

```bash
npm run tdlib:field-routing:generate
```

The generated registry lives in:

- `docs/04-data/tdlib-field-routing.catalog.json`: machine-readable route
  catalog for every TDLib object field, function request field, and function
  response.
- `docs/04-data/tdlib-field-routing.generated.md`: reviewable table form of
  the same registry.

The audit fails if the pinned TDLib schema hash changes, if TDLib counts change,
if an `Update` constructor is not assigned to exactly one projection group, or if
a TDLib function response type cannot be routed to a projection family. It also
fails if any generated field route is missing, points to an unknown physical
table, has no storage path, or introduces an `ignore` policy.

## Core Rule

Every TDLib input must have exactly one of these outcomes:

1. `projected`: all durable state in the update or response is written into
   domain projection tables.
2. `operation_effect`: the TDLib call returns no domain data, usually `Ok`; the
   domain state change is expected through TDLib updates.
3. `quarantined`: normalization failed or the TDLib schema is newer than the
   pinned catalog. The payload is retained only in a bounded diagnostic table
   until the model is fixed.

There is no successful "ignore" branch. There is also no permanent raw event log
for successfully normalized TDLib data.

## Normalization Contract

The ingestion path must route through an exhaustive dispatcher generated from or
checked against the pinned TDLib schema.

- Every `Update` constructor has a normalizer.
- Every `MessageContent` constructor has a content normalizer.
- Every TDLib function response is routed by return type.
- Unknown constructors are model bugs and go to quarantine with an alert.
- Successfully normalized payloads are not retained as raw TDLib JSON.
- Projection tables may store Telegram identifiers, TDLib constructor names,
  normalized scalar fields, typed child rows, and compact hashes for idempotency.

The target model stores data by Telegram domain semantics. It does not keep
compatibility envelopes, old response shapes, or duplicate raw/new
implementations.

## Control Tables

`telegram_schema_versions`

- Records the pinned TDLib schema commit, SHA-256, constructor counts, generated
  coverage counts, and migration timestamp.
- Gates startup and migration checks. A TDLib schema upgrade must update this
  document and the audit expectations in the same change.

`telegram_projection_gaps`

- Bounded quarantine for inputs that could not be projected.
- Stores constructor, source kind, Telegram ids when available, failure reason,
  first/last seen timestamps, occurrence count, and a short diagnostic payload
  sample.
- Has retention and alerting. It is not a replay log and not a product data
  source.

`telegram_procedure_observations`

- Normalized record of explicit TDLib calls when durable observability is
  required.
- Stores method, request correlation id, actor, response type, status,
  normalized scalar result fields, projected object ids, error code/message, and
  retention class.
- Complex response objects are projected into their domain tables; this table
  only links the call to those projections.

## Retention Policy

The target retention policy is normalized-state first:

- Durable domain facts stay in projection tables.
- Raw TDLib payloads from successful normalization are discarded.
- Quarantine rows are bounded and treated as defects.
- Operation observations have a retention class. State-bearing response objects
  survive in projection tables; transient operation metadata can expire.
- File bytes are not bulk-ingested by default. File metadata and Telegram file
  ids are durable; file downloads are request-driven.

## History State

History sync remains a separate domain. It may reference Telegram projection
tables through stable model refs, but it owns:

- `history_templates`
- `history_targets`
- `history_coverage`
- `history_backfill_jobs`

History does not own Telegram messages, chats, users, files, reactions, topics,
or TDLib state.

See [History](../03-domains/history.md).
See [History Schema](history-schema.md) for the table shape.

## Module-Owned State

Additional trusted modules own their tables and migrations. The table prefix
must match the module slug. The current pilot module owns:

- `summaries_runs`
- `summaries_results`
- `summaries_source_refs`
- `summaries_invalidations`

Other domains and modules must not read or write those tables directly.
